# 🌐 User Avatar Management Handler (`handler/handler.go`)

This module is responsible for handling the business logic related to user profile image updates (avatar uploads). It acts as the orchestration layer, coordinating file storage (S3/Cloud), authentication context retrieval, and database persistence.

---

## 🔍 Overview (System Design)

The `UserHandler` component is a core piece of the API gateway/service layer responsible for processing multipart form data uploads. Its primary role is to ensure that the upload process is atomic and sequential:

1.  **Authenticate:** Verify the user's identity and extract their ID from the request context.
2.  **Store:** Upload the raw file data to the designated cloud storage service (e.g., AWS S3).
3.  **Persist:** Update the user's record in the primary database with the publicly accessible URL generated by the storage service.

The handler decouples the HTTP concerns (request parsing) from the business concerns (storage and database write).

### 🖼️ High-Level Flow Diagram

```mermaid

    A[Client Request: POST /api/user/avatar] --> B{UserHandler.UploadAvatar};

## ⚙️ Detailed Logic Analysis

### `UserHandler` Structure
The handler is initialized with two critical dependencies, adhering to the Dependency Injection pattern:
*   `Repo *repository.UserRepository`: Handles database operations.
*   `Storage storage.FileStorage`: Handles external cloud interactions.

### `UploadAvatar(c *fiber.Ctx)` Step-by-Step

| Step | Action | Dependencies/Calls | Error Handling | Status Code |
| :--- | :--- | :--- | :--- | :--- |
| **1. Context Retrieval** | Extracts `user_id` from `c.Locals("user_id")`. | `c.Locals()` | Assumes middleware has already run and successfully attached the ID. | N/A |
| **2. File Extraction** | Retrieves the file object attached to the `avatar` form field. | `c.FormFile("avatar")` | If `err != nil`, returns 400 (Bad Request). | 400 |
| **3. Cloud Upload** | Uploads the file byte stream and returns the public access URL. | `h.Storage.UploadProfilePicture(...)` | If `err != nil`, returns 500 (Internal Server Error) indicating storage failure. | 500 |
| **4. Database Update** | Commits the generated URL to the `user` record. | `h.Repo.UpdateAvatar(...)` | If `err != nil`, returns 500 (Internal Server Error) indicating persistence failure. | 500 |
| **5. Success Response** | Logs the successful URL and returns a confirmation message. | `log.Printf()` | Success. | 200 |

## ⚠️ Warning & Tech Debt (Critical)

1.  **Fragile Type Assertion:** The line `userID := c.Locals("user_id").(string)` is a type assertion. If the preceding middleware fails to execute or fails to set the context value correctly, the application will panic at runtime (runtime crash) instead of returning a graceful 500 error.
    *   **Mitigation:** Implement proper nil checks or reflection checks on `c.Locals("user_id")` before casting.
2.  **Error Granularity:** The current error handling wraps all underlying service errors (Storage, Repo) into generic 500 responses. This is difficult for client-side consumption and monitoring.
    *   **Improvement:** Use custom error types (e.g., `StorageError`, `PersistenceError`) and map these to specific HTTP status codes (e.g., 422 Unprocessable Entity) to give clients better context.
3.  **Input Validation Scope:** This handler validates *if* a file was uploaded, but not the *content* or *type* of the file (e.g., limiting to JPEG/PNG, or checking max file size).
    *   **Improvement:** Implement robust MIME-type checking and file size limits *before* calling the expensive storage API.

---

## 📝 Note (Best Practices & Suggestions)

*   **Idempotency:** Consider implementing a check in the database transaction to see if the uploaded file is identical to the current avatar. If so, skip the storage call and return 200 immediately, saving unnecessary cloud API calls and bandwidth costs.
*   **Transaction Management:** If the storage upload succeeds, but the database update fails, the file remains in the cloud, creating "orphaned" data. The `UpdateAvatar` logic should ideally be wrapped in a transaction that handles rollback or, at minimum, a cleanup hook that deletes the uploaded URL from the cloud storage if the persistence layer fails.
*   **Logging Context:** While the successful URL is logged, it is beneficial to log the User ID and the original file name/size alongside the URL for better traceability during debugging.
