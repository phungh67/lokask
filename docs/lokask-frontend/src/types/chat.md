# 📚 Data Model Definitions: Chat & Scheduling Types (`src/types/chat.ts`)

This module centralizes the core data structures used across the application for managing conversational data, scheduling interactions, and housing AI-generated summaries. Maintaining these interfaces is crucial for type safety and system compatibility between frontend and backend services.

## 📋 Overview

This file defines three primary interfaces: `ScheduledCall`, `ChatMessage`, and `ConversationSummary`. These structures govern how scheduled video/voice calls are tracked, how individual chat messages are formatted for display, and how AI processes distill the essence of a full conversation.

| Interface | Purpose | Usage Context | Primary Owners |
| :--- | :--- | :--- | :--- |
| `ScheduledCall` | Tracks the lifecycle and metadata of a planned interaction (call). | Booking Flow, Dashboard, Calendar Components. | Scheduling Service, Core Backend. |
| `ChatMessage` | Represents a single message sent within a conversation thread. | Chat Widgets (Frontend), Messaging API Endpoints. | Chat Service, API Gateway. |
| `ConversationSummary` | Stores the high-level, actionable takeaways generated by an AI model after a chat session. | Dashboard Summary View, Post-Chat Follow-up Widgets. | AI Processing Pipeline, Reporting Service. |

***

## 💡 Detail

### 1. `ScheduledCall`

Defines the state and details of an appointment or planned consultation.

| Property | Type | Description | Constraints / Notes |
| :--- | :--- | :--- | :--- |
| `id` | `string` | Unique identifier for the scheduled call. | Required. Primary key. |
| `conversationId` | `string` | ID linking the call to a specific chat thread. | Foreign Key to `Conversation` table. |
| `type` | `"video" | "voice"` | The medium through which the call will take place. | Must be one of the two defined values. |
| `scheduledAt` | `Date` | The date and time the call is set to occur. | Must be timezone-aware. |
| `duration` | `number` | Expected length of the call in minutes. | Must be $> 0$. |
| `status` | `"confirmed" | "pending" | "cancelled" | "completed"` | The current status of the booking. | Must be one of the four defined values. |
| `notes` | `string?` | Additional notes related to the call (e.g., pre-reading material). | Optional. |
| `createdAt` | `Date` | Timestamp when the record was created in the system. | Required. |

### 2. `ChatMessage`

Defines the structure of a single message payload, accommodating rich content types (text, image, map).

| Property | Type | Description | Notes / Backend vs. Frontend |
| :--- | :--- | :--- | :--- |
| `id` | `string | number` | Unique ID for the message. | Backend MUST ensure uniqueness. |
| `conversation_id` | `string` | The conversation thread ID. | Required. Partitioning key for chat retrieval. |
| `sender_id` | `string` | ID of the user who sent the message. | Required. |
| `content` | `string` | The main textual content of the message. | Required. |
| `is_read` | `boolean` | Tracks if the recipient has viewed the message. | Crucial for read receipts logic. |
| `created_at` | `string` | Timestamp of message creation (ISO 8601 format). | Backend must maintain consistency (e.g., UTC). |
| `sender` | `"user" | "consultant" | "traveler"` | **(Frontend Helper)** Role of the sender. | Added for simplified display logic. |
| `timestamp` | `Date?` | **(Frontend Helper)** Parsed date object for display. | Should ideally be derived from `created_at`. |
| `type` | `"text" | "image" | "map"` | **(Frontend Helper)** Indicates content type. | Determines how the UI renders the message. |
| `imageUrl` | `string?` | URL for image attachments. | Used if `type` is `image`. |
| `mapData` | `{...}` | Detailed structured data for location sharing. | Used if `type` is `map`. See object definition below. |

### 3. `ConversationSummary`

The result of the AI processing pipeline, distilling key insights from the raw chat history.

| Property | Type | Description | Purpose / AI Function |
| :--- | :--- | :--- | :--- |
| `preferences` | `string[]` | Array of key traveler preferences detected (e.g., "local food", "hiking"). | Helps backend personalize future recommendations. |

## ⚠️ Warning & Tech Debt

1.  **Schema Drift Risk:** The `ChatMessage` interface mixes required backend fields (`id`, `conversation_id`, `created_at`) with optional, frontend-helper fields (`sender`, `timestamp`, `type`, `imageUrl`, etc.). This separation increases the risk of schema drift. **Action:** We must enforce strict validation on the backend to ensure that front-end helper fields are only consumed for display and never used for primary data integrity.
2.  **Timestamp Consistency:** Both `ChatMessage` and `ScheduledCall` rely on `Date` objects or string timestamps. We must standardize *all* time persistence (database, API payload, service calls) to **UTC ISO 8601 format** to avoid timezone-related bugs when operating across different global regions.
3.  **AI Model Versioning:** The `ConversationSummary` relies entirely on the output of an external AI service. We must formalize a versioning contract for this summary generation process. If the AI prompt changes, the consumers of this summary must be updated simultaneously.

## 📝 Note

*   **Read/Write Segregation:** For robust API design, consider generating specialized DTOs (Data Transfer Objects) for reads (`ChatMessageReadDto`) versus writes (`ChatMessageCreateDto`). While the single interface is convenient for documentation, separating these types will greatly enhance backend type safety and validate payload structures explicitly.
*   **Future Expansion:** We might need to expand `ChatMessage` to include a `attachment` field that can encapsulate both images and documents (PDF/ZIP) rather than handling them separately via `imageUrl` or custom logic.
