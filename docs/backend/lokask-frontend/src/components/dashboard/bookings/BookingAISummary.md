## ⚙️ Booking Summary Service Documentation

### 1. Core Business Logic (The Summary Generation Flow)

The primary goal is to transform unstructured conversational data (the entire chat transcript) into a structured, concise summary of critical booking details.

**Input Data:**
1.  `BookingID` (Identifier for the booking context).
2.  `ConversationHistory` (An array of structured messages, including sender, timestamp, and content).

**Process Flow (`GenerateBookingSummary`):**

1.  **Context Retrieval:** The service retrieves the last N messages of the conversation associated with the `BookingID`.
2.  **Prompt Engineering:** A meticulously crafted system prompt is constructed. This prompt instructs the LLM not just to summarize, but to extract specific data points (e.g., Dates, Attendees, Services, Special Requests) and return them in a highly predictable, parsable format (e.g., JSON).
3.  **AI Invocation:** The system sends the combined prompt and context history to the configured external AI Provider API (e.g., OpenAI, Gemini).
4.  **Response Parsing:** The backend service handles the streamed or batch response, deserializes the resulting JSON/text payload, and validates the extracted data against expected schemas.
5.  **Format Transformation:** The raw structured data is transformed into the final simple `[]string` array expected by the frontend component.

### 2. API Surface Definition

The summary generation should be exposed via a RESTful API endpoint, ideally triggered only when the conversation window is closed or a summary is explicitly requested.

**Endpoint:**
`POST /api/v1/bookings/{bookingId}/summary`

**Request Body (`SummaryRequest`):**
```json
{
  "conversation_history": [
    {
      "sender": "user",
      "content": "I need a booking for two people next Friday.",
```

**Success Response (200 OK):**

### 3. Backend Architecture & Repository Pattern (Go Implementation)

To ensure clean separation of concerns, we will use a layered architecture (Repository $\rightarrow$ Service $\rightarrow$ Handler).

#### A. Data Structures (Go)

```go
package models

import "time"

// ConversationMessage represents a single turn in the chat history.
type ConversationMessage struct {
    Sender    string    `json:"sender"` // "user" or "agent"
    Content   string    `json:"content"`
    Timestamp time.Time `json:"timestamp"`
}

// SummaryRequest holds the data required to initiate the summary generation.
type SummaryRequest struct {
    ConversationHistory []ConversationMessage `json:"conversation_history"`
}

// SummaryResponse is the data structure returned to the client.
type SummaryResponse struct {
    Status       string   `json:"status"`
    SummaryItems []string `json:"summary_items"` // Directly maps to the frontend requirement
}
```

#### B. Repository and Provider Interfaces

We define interfaces to abstract external dependencies, adhering to the Dependency Inversion Principle.

```go
package repository

// ConversationRepository defines methods for retrieving chat history data.
type ConversationRepository interface {
    GetHistoryByBookingID(bookingID string) ([]models.ConversationMessage, error)
}

// AIProvider abstracts the interaction with the external LLM service.
type AIProvider interface {
    // GenerateSummary calls the external API with context and prompt instructions.
    // It should handle API keys, request formatting, and streaming/rate limiting.
    GenerateSummary(context string, prompt string) ([]string, error)
}
```

#### C. Service Layer Implementation (The Orchestration)

The service layer handles the complex business logic, coordinating data retrieval and external API calls.

```go
package service

// BookingSummaryService handles the business logic for generating the summary.
type BookingSummaryService struct {
    Repo repository.ConversationRepository
    Provider repository.AIProvider
}

// NewBookingSummaryService initializes the service with required dependencies.
func NewBookingSummaryService(repo repository.ConversationRepository, provider repository.AIProvider) *BookingSummaryService {
    return &BookingSummaryService{
        Repo:     repo,
        Provider: provider,
    }
}

// GenerateSummary is the primary method called by the API handler.
// It executes the full logic flow: Retrieve -> Prompt -> Call -> Parse.
func (s *BookingSummaryService) GenerateSummary(bookingID string) (*models.SummaryResponse, error) {
    // 1. Retrieve History
    history, err := s.Repo.GetHistoryByBookingID(bookingID)
    if err != nil {
        return nil, fmt.Errorf("failed to retrieve conversation history: %w", err)
    }
    
    // 2. Construct Context String
    context := s.buildContextString(history) 
    
    // 3. Define Prompt (This is the core logic)
    prompt := s.constructSystemPrompt()
    
    // 4. Call AI Provider
    summaryItems, err := s.Provider.GenerateSummary(context, prompt)
    if err != nil {
        return nil, fmt.Errorf("failed to generate summary from AI provider: %w", err)
    }

    // 5. Return structured response
    return &models.SummaryResponse{
        Status:       "success",
        SummaryItems: summaryItems,
    }, nil
}
```
